0. The winning thesis

Every other team built an upright person at a desk. We build for space.

We scanned all 22 public repos for PS 26174. They share one architecture: webcam → YOLO or colour detection → MediaPipe hands → rules → dashboard. None of them tests a rotated or inverted astronaut, and none actually runs HMR. Their datasets are 170–550 frames from a single room.

Our system is the only one that:

  1. generates labelled training data at any crew orientation from a 3D digital twin (22,349 frames),
  2. trains and tests on orientations the model never saw,
  3. runs HMR for real on a laptop GPU.

The 24 hours go to closing our one gap against them (a trained object detector and a live real-prop demo) and making all of this visible.

2. Architecture, end to end

Full box-and-arrow diagram, with the HMR branch and the training pipeline: architecture.html

Hardware
Fixed payload camera clamped to the rack (1080p USB) · printed ArUco marker on the rack · edge computer (RTX 3050 laptop now, Jetson Orin class for flight) · speaker · LAN link to a "ground" receiver.
↓
Rack frame
ArUco pose → camera-to-rack transform. Every coordinate after this point is rack-relative. The existing geometry normaliser (pipeline/rack_frame.py) is the fallback when the marker is hidden.
↓
Perception (CNN)
YOLOv8n, 4 classes: main_box_closed, main_box_open, red_box, yellow_box. It replaces the colour detector.
MediaPipe Hands + Pose for hands and body (with the roll correction already in upright_pose.py).
ROMP HMR as an optional 3D body channel: run on a cropped, rotation-corrected person patch (not the raw frame), triggered adaptively rather than on a fixed schedule, with automatic 2D fallback when it loses the body. See architecture.html §2 for why this fixes speed and accuracy together.
↓
Features
pipeline/features.py (shared by training and live, byte-identical, tested). Layout pose132+obj11: 3 boxes × (x, y, visible) + 2 hand-to-box distances. YOLO produces the same 11 numbers the colour detector did, so the LSTM input format doesn't change and the parity tests still hold.
↓
Temporal (LSTM)
LSTM over 2–3 s windows on a fixed 100 ms clock. Ensemble of 3 seeds (average their probabilities), which directly attacks the 0.38–0.60 seed spread we measured. Exported to ONNX.
↓
Protocol judge
Deterministic state machine: a step is confirmed only after N consistent windows above threshold. It classifies deviations (skipped, out of order, repeated, wrong object), gives recovery guidance, and never lets one bad frame corrupt the state.
↓
Outputs
Qt dashboard · offline voice (pyttsx3) · JSONL + TXT log (kilobytes) · UDP stream to a set IP · local MP4 recording.

Why hybrid: learning handles what's fuzzy (seeing boxes, recognising motion), and rules handle what's safety-critical (sequence judgement). A pure end-to-end video model would need thousands of real takes and couldn't explain its alerts. Every alert can say why.

3. The AI model (the graded deliverable)

Model card

  • Name: BAS-HAR v1 = YOLOv8n detector + LSTM step classifier (3-seed ensemble)
  • Input: fixed-camera video, any frame rate (resampled to 10 Hz)
  • Output: step 1–8 or idle, with confidence, every 100 ms
  • Size: YOLOv8n ~6 MB, LSTM <1 MB each, ONNX
  • Runs on: RTX 3050 laptop, fully offline
  • Trained on: 23 Blender takes at every orientation + real webcam takes
  • Tested on: held-out orientations (180° roll, −60° roll, 90° yaw, 60° pitch) + skip/recover sequences

What we report (targets, not promises)

  • Step accuracy on held-out orientations: mean ± spread of 3 seeds (baseline 0.38–0.60)
  • Detector recall per class (baseline yellow box ≈ 0.15)
  • Skip / out-of-order detection recall on error takes
  • False alerts per run
  • End-to-end latency and fps on the RTX 3050

Event-level metrics (deviation recall, false alarms) matter more than frame accuracy. Only 2 of 22 competitors even define them.

Why this will work: our own evidence

0.555

Held-out accuracy from box signals alone, with a detector that misses 85% of yellow boxes. Better box detection is the biggest lever.

0.23

Pose alone. Pose helps, but it isn't what decides the step.

~0.80

With perfect inputs. The LSTM and features are fine, and perception is the bottleneck.

Training recipe

# 1. YOLO labels from Blender ground truth (new script, ~30 lines)
python tools/export_yolo_labels.py --dataset dataset/blender_core --out dataset/yolo_boxes
# 2. Train the detector (synthetic + ~300 real frames)
pip install ultralytics PyQt6
yolo detect train model=yolov8n.pt data=dataset/yolo_boxes/data.yaml epochs=40 imgsz=640 device=0
# 3. Rebuild sequences with YOLO boxes, train 3 seeds, score held-out
tools/retrain_and_evaluate.sh dataset/blender_core orient_180,orient_-60,yaw_90,pitch_60

5. Hardware

Demo rig (build tonight, ~₹500)

  • Mock payload rack: a foam board or cardboard panel (~60×80 cm) with velcro strips, like an ISS rack face
  • ArUco marker (A5 print) fixed to the rack corner
  • Props: a main box with a hinged lid, plus a red and a yellow small box
  • Camera: 1080p USB webcam clamped to the rack (fixed-payload camera, never handheld)
  • Lighting: a desk LED lamp, switched off to demo a lighting failure
  • Edge computer: the RTX 3050 6 GB laptop, Wi-Fi off during the demo
  • "Ground station": a second laptop or phone running VLC on udp://@:5000
  • Speaker for the voice alerts

Flight path (for the PPT, clearly labelled as projected)

  • Target: NVIDIA Jetson Orin class module (edge GPU, 7–25 W)
  • Path: ONNX → TensorRT FP16. YOLOv8n and the LSTM are both tiny.
  • Cameras: rack-fixed, so the rack frame is calibrated once per payload
  • Downlink: only the log (KB) + an optional low-bitrate stream. Raw video stays on board.
  • Measured numbers come from the RTX 3050. Never present Jetson numbers as measured.

P5 runs in parallel, hours 0–10: crop ROMP's input to YOLO's person box, rotate it upright using MediaPipe's shoulder–hip vector, and gate ROMP's calls on how fast that angle is changing instead of a fixed schedule (architecture.html §2). By H10, measure detection rate before/after on the 8 HMR_UNRELIABLE_TAGS takes — this doesn't block P1–P4's critical path, but it's what turns the HMR side panel from "runs sometimes" into "runs correctly and fast".

Gates:

  • H7: if YOLO yellow recall isn't clearly above 0.15, spend 2 more hours on real labels and stop tuning.
  • H10 — measured, fixed once, then hit a real limit: the crop+rotate fix clearly helped 2 of 8 takes (both roll-near-inversion: orient_180 tracked 0.37→0.60, light_single_fail_180 0.23→0.48), did nothing for 5 takes already near zero (moderate 30–90° roll, dim lighting — ROMP has no representation for these poses at all, not a framing problem), and initially made pitch_60 worse (0.74→0.21). Root cause found and fixed: ROMP's confidence doesn't detect a badly-framed crop, so every real run now also tries the plain full frame and keeps whichever scores higher — recovered pitch_60 to 0.37. Tried shortening the re-run interval to close the remaining gap to 0.74; it made things worse (0.22), proving ROMP's own per-call accuracy on this orientation is inconsistent regardless of call frequency — not a tunable scheduling parameter. Full numbers and reasoning: architecture.html §3. Verdict: ship the full-frame-fallback fix (real, verified, no-downside) as a targeted roll/inversion improvement, stop tuning the scheduler further, and don't claim HMR "handles orientation" broadly — the 2D fallback is what actually carries the cases ROMP can't.
  • H12: if the ensemble doesn't beat 0.53, ship the ensemble we have and let the rule layer run on detector object states, which is reliable on real footage.
  • H14: after this, no new features. Only the demo and the story.

LSTM accuracy stays low on held-out orientationsReport it honestly with the spread. The demo runs on detector states + rules, and the story is the method plus the honest test.
Live demo fails in front of judgesReplay mode on a recorded take + the pre-recorded video
HMR loses the body in the demoThat's the designed behaviour: the panel shows "HMR lost → 2D fallback" and keeps working
GPU memory full with YOLO + MediaPipe + HMRThe crop+adaptive scheduler already cuts ROMP calls sharply; if still tight, drop to a fixed low rate or turn HMR off for the live run
Running out of timeCut in this order: HMR panel → camera rotation shot → sideways takes. Never cut the live skip-alert demo.

13. Judge Q&A: prepare these answers

They askWe answer
How does this work in microgravity?Everything is measured relative to the rack, not the floor. Trained at every orientation, and here are the results on orientations it never saw.
Why not a single end-to-end video model?It would need thousands of real takes and can't explain its alerts. Ours learns perception and keeps the safety logic auditable.
How accurate is it?Give the held-out numbers with the seed spread, and explain why held-out orientation is the honest test.
Why is HMR optional?We run it (ROMP), we measured where it fails (strong tilt, inverted), and the system falls back automatically. Rack-frame features carry the orientation problem.
Synthetic data won't match reality.That's why we fine-tune on real takes and test on real takes. Blender covers orientations you can't film on Earth.
How do we add a new experiment?Write a protocol file, render it in the digital twin, record a few real takes, retrain. Hours, not weeks.
What hardware would fly?An edge GPU module (Jetson Orin class) via ONNX/TensorRT. The demo numbers are measured on a laptop GPU.
Privacy / bandwidth?Raw video stays on board. Only a kilobyte log and an optional stream leave.

14. What we don't do

  • No LLM, no face recognition, no life-support panels. Competitors did that, and it's scope creep.
  • No more Blender showcase renders and no more HMR tuning.
  • No accuracy number without its test split and seed spread.

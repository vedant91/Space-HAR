2. How HMR fits

  • What it adds: a 3D body measured against the rack. That gives us the astronaut's attitude (roll, pitch, yaw relative to the rack) and 3D wrist positions when 2D keypoints are unreliable. It also drives the 3D panel in the dashboard.
  • When it's used: the fusion gate decides every frame. If the 3D backend is confident, we use its 3D wrists and attitude. Otherwise we use MediaPipe 2D.
  • Which 3D backend: as of this build, train/hmr3d_model.py — our own model, trained on our synthetic ground truth — not ROMP. See section 3 for why, and the honest before/after numbers.
  • When it still fails: exactly 90° roll (both directions) and dim lighting at 90°. 60° roll used to fail too — closed by denser training data, see below. Not a framing problem at 90° either — MediaPipe tracks the body fine there too — likely a genuine information limit of a single fixed camera at that exact edge-on viewing angle. The 2D branch with roll correction takes over, and the step decision keeps working because it's driven mostly by boxes and hands.
  • Training consequence: the LSTM must be trained on the same fused features it will see live, both with and without HMR. Otherwise switching HMR on changes its input and accuracy silently drops. The builder records this as its own pose source (fused), and the existing load-time guard enforces it.

Why it's slow and wrong at the same time, and the fix

Built and verified this session (pipeline/hmr_backend.py) — one correction to the original design below: MediaPipe's own landmarks are the real per-frame tracker, not a stock YOLO person-detector. Measured directly on dataset/blender_core: stock COCO YOLOv8n almost never calls the rendered, suited astronaut a person at all (it guesses things like "traffic light"). YOLO only proposes a box as a re-acquisition attempt after MediaPipe's own track is lost for too long — it isn't the primary signal.

  • MediaPipe drives tracking every frame, essentially free — it already runs for hands elsewhere in the pipeline. Its landmark box and shoulder-hip angle are EMA-smoothed (weight 0.5) so the crop doesn't jitter frame to frame.
  • Stock YOLO is a fallback only, tried after 5 consecutive frames with no usable landmarks (TRACK_MAX_COAST), and dropped back to a full-frame search if that also fails. On these renders it rarely finds anything — MediaPipe is doing the real work.
  • ROMP only ever sees a small, upright, tracked crop (padded to 1.3× the landmark box's diagonal, so any rotation still fits), never the raw 1080p frame. This is the single highest-leverage change: an order-of-magnitude fewer pixels for the backbone to process, and the upright, well-resolved body it was actually trained to expect.
  • Low-confidence retry. If ROMP's confidence on the corrected crop is still below 0.1, it tries three more rotation hypotheses (±90°, 180°) and keeps the best — catching cases where the torso-angle estimate itself was wrong (MediaPipe flipped on an inverted body, for instance).
  • The scheduler re-runs ROMP only when it needs to: the tracked angle has drifted more than 15° since the last run, or a full second has passed, whichever comes first. An astronaut holding still while examining a box (most of a step) costs nothing; a fast tumble triggers frequent re-checks.
  • Measured on all 8 takes — the result is real, and it's mixed, not a clean win. "Detection rate" reads 1.00 everywhere before and after, which the measurement script's own docstring warns about: at this threshold ROMP always claims to find someone, including false locks onto rack geometry. The real metric is median upper-body joint error against Blender's ground truth pose, in units of torso length ("tracked" = under 0.5 torso).

Honest read: the fix helps specifically where the failure is roll near full inversion (180°) — the two takes that improved are both roll-dominant. It does nothing for moderate roll (30–90°) or dim lighting at high roll — those 5 takes were already near zero and stayed there; something ROMP's training simply never covers, not a framing problem the crop could fix. It regressed pitch_60 at first (0.74 → 0.21): ROMP's confidence measures "a person-shaped blob is here", not "this crop is framed correctly", so a foreshortening-mangled crop under pitch scored confidently while being spatially wrong.

Fix applied and verified (ROMP_CONTRACT_VERSION=3): every actual ROMP run now also tries the plain, uncropped full frame — exactly what the code did before any of this existed — and keeps whichever result ROMP itself is more confident in. This bounds the accuracy floor at the pre-crop behaviour by construction (a dedicated test proves the full-frame candidate wins when it scores higher, not just that the code runs). Re-measured: pitch_60 recovered to 0.37 (up from the 0.21 regression), while orient_180 (0.60) and light_single_fail_180 (0.48) held their gains.

But 0.37 is still well below the 0.74 pre-crop baseline, and that gap turned out not to be fixable by more scheduling. Pitch_60 only actually calls ROMP on ~3% of frames (pitch doesn't create the in-plane rotation the scheduler watches for, so it rarely re-triggers), and the "tracked" number is extrapolating those few calls across the whole clip. Testing a much shorter staleness window (more frequent re-runs) made it worse (0.22), not better — proving this isn't a tunable scheduling parameter. ROMP's own per-call accuracy on this orientation is genuinely inconsistent, frame to frame, regardless of how often it's asked. That's a limit of ROMP's pretrained weights on an orientation it was never trained on, not an input-engineering problem.

What this means for the plan: the full-frame-fallback fix is a real, verified, no-downside improvement — keep it. Don't keep tuning the scheduler further; the evidence says that lever is exhausted. Don't ship this as "HMR now handles orientation" — it measurably helps only roll-near-inversion. Moderate roll, dim lighting, and full pitch reliability remain unsolved by ROMP as-is; the graceful 2D fallback (already built into the fusion gate) is what actually carries those cases, which is exactly what it's there for.

The real fix: stop using ROMP

Rather than fine-tune ROMP's own weights (not practically accessible through the simple_romp package, and a much larger undertaking regardless), we trained our own model from scratch: train/hmr3d_model.py, a MobileNetV3-Small backbone fine-tuned entirely on our own synthetic ground truth (pose_2d.npy — exact joint positions ROMP's original training data never had for this subject at all). It replaces ROMP as the HMRBackend's primary path; the crop/track/schedule machinery above is unchanged, only the model running on the crop is different.

Trained honestly: the exact 8 takes ROMP fails on, plus take_0022 (a different camera entirely), were held out of training completely — a first training run that accidentally left 7 of these 8 takes in the training set gave a misleadingly high 96% number, caught before being reported, and retrained correctly. The numbers below are from that honest, retrained checkpoint (models/hmr3d_net.pt), scored with tools/measure_hmr_crop.py --backend custom, same metric as ROMP's numbers throughout this page.

Honest read: on every one of these 8 takes, the custom model matches or beats ROMP — never worse. Round one moved the wall outward: 30° roll now works well, where before it was near zero. Round two tested whether that wall was a real limit or a data gap — we rendered 10 more takes at 40°/50°/65°/75°/85° roll (both directions) and retrained. 60° roll went from completely untracked (0.00) to 0.77 — the single largest single change measured on this system — and −90° moved from 0.00 to 0.22. It was a data gap, not a hard limit, for 60°. But exactly 90° roll stayed stuck (0.07, and 0.02 under dim light) even with 75° and 85° now bracketing it in training. MediaPipe's own tracking is still reliable there too (mp_hit 0.90–1.00) — at precisely edge-on to one fixed camera, one whole side of the body is nearly fully self-occluded, which looks like the real information limit, not something denser sampling alone fixes. Speed is comparable to ROMP (55–192ms/frame).

Two other checkpoints exist for reference, not for shipping: models/hmr3d_net_interp_only.pt (the first, methodologically invalid run — kept only so the mistake and its correction are traceable) and models/hmr3d_net_fairtest.pt (identical weights to the shipped hmr3d_net.pt, saved under its original training-run name).

3. Training: how the models are made

The sequence builder runs the trained detector rather than the Blender ground-truth boxes, so the LSTM learns from the same imperfect detections it will see live.

4. Borrowed from a competitor, adapted to our numbers

A competitor repo (Orion — the strongest one found) uses Shannon-entropy gating on its temporal classifier's confirmation logic. Worth taking: a single scalar confidence can clear its threshold while the rest of the probability distribution is still spread across several other classes — that frame is noise wearing a confident number, and a top-1 check alone can't tell the difference.

What we built (pipeline/state_machine.py, config.STEP_ENTROPY_MAX) — re-derived for our own 9-class problem (8 steps + idle) rather than copying their number, which was tuned for their 8-class model:

  • The LSTM's full softmax entropy now rides alongside its confidence into feed_prediction(), as an optional keyword argument that defaults to None — every existing caller (tools/evaluate_real.py, simulation/space_sim.py, tools/showcase_overlay.py) is completely unaffected unless it opts in.
  • Worked example at our class count: top-1 confidence 0.65 (right at the existing threshold), remaining 0.35 spread over just one other class → entropy 0.65 nats, a decisive two-way call, passes. The same 0.65 top-1 spread uniformly over all 8 other classes → entropy 1.38 nats, genuinely shapeless, fails. STEP_ENTROPY_MAX = 1.4 sits just above that second case.
  • Verified: a self-test in pipeline/state_machine.py (python -m pipeline.state_machine) proves a step is blocked at high entropy and confirmed at low entropy, at the identical confidence value both times — and that omitting entropy entirely reproduces the exact old behaviour. Full suite (pytest, 49 tests) stays green.

Not borrowed: Orion's 2D torso-centred normalization for microgravity invariance — it's self-referential (relative to the astronaut's own body, computed from a 2D pose estimator with the same upright-training bias as ours) rather than relative to an external structure. Our rack-anchored frame already does what theirs can't: express "box in the target zone on the rack," which has no meaning in a body-only reference frame.
